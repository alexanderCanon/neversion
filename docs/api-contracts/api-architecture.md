# 🧠 Neversion API Architecture Protocol

This professional guide dictates the design patterns, error handling standards, and development workflow for the entire Neversion backend API ecosystem.

---

## 🏗️ 1. Core Principles

- **Contract-First Development:** The API is the product; the code is merely the implementation. No code should be written before the JSON requests and responses are defined in the specific `docs/api-contracts/*.md` module files.
- **Markdown as Source of Truth:** We have moved away from massive autogenerated Swagger/OpenAPI files in favor of modular, domain-specific markdown contracts. The markdown files dictate the backend implementation.
- **Consistency:** All controllers must share a uniform structure for responses, consistent HTTP verbs, and decentralized security logic.

---

## 🔗 2. API Design & Routing

### Versioning
All APIs are versioned locally via the URI path to ensure backward compatibility:
* **Standard:** `/api/v1/{module}`
* **Rule:** Breaking changes (changing field types or removing fields) strictly require a bump to `/v2`.

### REST Semantics
Endpoints must adhere to pure REST structures.
* **Recommended Response:** 
  ```json
  {
    "orderId": "123",
    "status": "PENDING"
  }
  ```
* **Anti-Pattern (DO NOT USE):**
  Avoid wrapping payloads in generic metadata wrappers. It breaks pure REST semantics and adds unnecessary parsing layers:
  ```json
  // AVOID THIS
  {
    "success": true,
    "data": { "orderId": "123" }
  }
  ```

## ❗ 3. Standardized Error Handling (RFC 7807)

The API strictly implements the **RFC 7807 (Problem Details)** standard across the entire global exception handler.

### 3.1. Field Validation Errors (`400 Bad Request`)
If a payload fails constraint validation, the response must return a `fieldErrors` array detailing exactly what went wrong for the client UI.
```json
{
  "status": 400,
  "type": "validation-error",
  "title": "Bad Request",
  "detail": "Invalid fields detected",
  "fieldErrors": [
    {
      "field": "price",
      "message": "Price cannot be negative",
      "rejectedValue": -50
    }
  ]
}
```

### 3.2. Business Logic Violations (`409 Conflict`)
To ensure consistency in domain rules (e.g., overriding a blocked slot) or referential database integrity, custom exceptions like `BusinessRuleException` MUST explicitly trigger a **`409 Conflict`**.

### 3.3. Resource Lookup (`404 Not Found`)
Attempting to act on a UUID that does not exist MUST trigger a clean `404 Not Found`.

## 🚀 4. The Development Workflow

1. **Design the Contract:** Write the expected JSON payloads, DTO models, and HTTP logic into the respective module inside `docs/api-contracts/`.
2. **Review:** Ensure the endpoints align with Neversion's **Business Rules** documented in the main `docs/`.
3. **Implement:** Write the Spring Boot controllers and DTOs mapping exactly to the contract.
4. **Test:** Create Integration Tests (`*IT.java`) testing those exact bounds.
5. **Deploy:** Containerize and release.

> *"If the contract is wrong, the system is wrong."*
