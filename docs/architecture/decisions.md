# Architectural Decision Records (ADRs)

Este documento registra las decisiones de arquitectura tomadas para el sistema **Neversion**, basadas en la visión de despliegue y el descubrimiento.

| ID | Título | Estado | Contexto | Decisión | Consecuencias |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **ADR-01** | Arquitectura Desacoplada (Backend/Frontend) | **Confirmed** | Necesidad de soportar múltiples interfaces (Panel Admin y Tienda Cliente) y futura escalabilidad. | Uso de Spring Boot para el API Backend y Angular para las SPAs de Frontend. | Mayor flexibilidad en el despliegue y separación clara de responsabilidades. |
| **ADR-02** | Estrategia de Multi-tenancy | **Confirmed** | El sistema debe permitir que múltiples vendedores operen con su propia marca e inventario aislado. | Implementación de aislamiento de datos mediante `vendor_id` en todas las entidades core y operativas. | Garantiza la privacidad de datos entre negocios; requiere validación constante de pertenencia en el API. |
| **ADR-03** | Validación de Pagos Manual | **Confirmed** | El negocio actual opera con depósitos y transferencias en Guatemala (GTQ). | El flujo requiere que el cliente suba un comprobante y el vendedor lo apruebe antes de generar la orden. | Evita la complejidad de integraciones bancarias iniciales; introduce un paso operativo manual. |
| **ADR-04** | Asignación de Accesos Semiautomática | **Confirmed** | Se busca reducir el error humano pero manteniendo el control final del vendedor. | El sistema sugiere el recurso disponible más apto, pero el vendedor debe confirmar la asignación final. | Equilibrio entre automatización y control; permite al vendedor decidir qué cuenta/perfil entregar. |
| **ADR-05** | Persistencia Relacional y Gestión de Migraciones | **Confirmed** | Necesidad de integridad referencial y trazabilidad operativa de suscripciones. | Uso de PostgreSQL (vía Supabase) gestionado mediante Flyway para migraciones de esquema. | Garantiza consistencia de datos y facilidad de evolución del esquema de forma controlada. |
| **ADR-06** | Autenticación Externa | **Confirmed** | Delegar la complejidad de la gestión de identidades y seguridad de contraseñas. | Uso de **Supabase Auth** validando tokens JWT en el backend. | Reduce riesgo de seguridad y minimiza proveedores al reutilizar Supabase (ya usado para PostgreSQL). |
| **ADR-07** | Regla BR-07 como Constante de Aplicación | **Confirmed** | El valor de gracia para renovación tardía (2 días) no necesita ser configurable por vendedor en el MVP. | El valor se define en `application.yml` del backend, no en la base de datos. | Simplicidad inmediata; migrable a tabla `VENDORS` en el futuro sin romper nada. |
| **ADR-08** | RBAC Implícito por Rol | **Confirmed** | Solo existen 3 roles (super_admin, vendor, client) con alcances claramente separados. | Los permisos se implementan como guards en el backend basados en el campo `role` de `USERS`. Sin tabla de permisos. | Evita sobreingeniería; si se necesitan permisos granulares en el futuro, se puede introducir una tabla de permisos. |
| **ADR-09** | Proveedor de Auth: Supabase Auth | **Confirmed** | Se necesita un proveedor de identidad externo para manejar registro, login y tokens. | Uso de **Supabase Auth** como proveedor de autenticación. | Minimiza proveedores (Supabase ya maneja la DB). Emite JWT que el backend valida. |
| **ADR-10** | Proveedor de Email: Resend | **Confirmed** | Se necesita un servicio de envío de correos transaccionales para notificaciones del sistema. | Uso de **Resend** como proveedor de email transaccional. | API moderna, pricing accesible para MVP, excelente DX. Todo envío queda registrado en `notification_log`. |
